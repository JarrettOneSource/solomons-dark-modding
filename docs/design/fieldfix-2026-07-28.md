# Multiplayer locomotion field fix and loading screen

Date: 2026-07-28
Issues: #69, #70

## #69 regression chain

The player-family actor path in the original game is not a plain transform
write. `PlayerActorTick` (`0x00548B00`) checks the movement vector at actor
offsets `+0x158/+0x15C`, dispatches one of the compiled `Step1`/`Step2` sound
objects on the native 25-frame cadence, and calls `PlayerActor_MoveStep`
(`0x00525800`). The movement step maintains the actor's native spatial
presence, including its movement-cell-grid membership. The recovered native
extended collision query is at `0x005238C0`; the cell-grid rebind is at
`0x005217B0`.

The regression arrived in two independent landings:

| Date | Landing | Effect |
| --- | --- | --- |
| 2026-05-28 | `6d4d5999e4152bd6b5d9b581a0f4d92b2005d6fc` | Introduced remote participant playback as direct `x/y` writes followed by a cell-grid rebind. The same landing's central participant response still separated a moving local player from a native remote, and the remote's replicated movement vector could still reach the stock tick, so the two owner-visible behaviors happened to remain present. |
| 2026-06-03 | `2fff5a4752664769d8f77b4cc3644b6011c2f7ea` | Expanded the pre-stock-tick movement-vector clear to every native remote (`native_remote_binding || loader_owned_movement_vector_present`). The remote could no longer enter the stock footstep/step path, so remote footsteps stopped. |
| 2026-07-11 | `5a6a133cbab84c1aabc487ca372526200d876183` | Skipped every local-player/native-remote pair in the central participant collision response to prevent a previous cross-instance push/replicate oscillation. Since stock player-family movement uses collision mask `1` and does not itself separate same-family actors, the remaining response was removed and players could walk through remote mirrors. |

The underlying ownership error was broader than either symptom: remote and
synthetic participant controllers owned actor transforms, but there was no
single player-family locomotion seam responsible for native movement,
spatial presence, and movement presentation.

## #69 fix

`player_family_locomotion.inl` is now the owning seam for every loader-moved
player-family actor:

- `EnsurePlayerFamilyActorNativePresence` restores the alive registration state
  and cell-grid membership before movement.
- `MovePlayerFamilyActorThroughNativeStep` moves through the recovered native
  `PlayerActor_MoveStep`, measures the actual displacement, and dispatches the
  native-equivalent footstep only when the actor moved and the native cadence
  allows it.
- `TeleportPlayerFamilyActorAndRebind` is reserved for discontinuities and
  explicit transform updates, then restores/rebinds native presence.

Remote participant playback and Lua-bot movement both use this seam. Entity
transform requests use its teleport path, so a caller cannot silently leave a
player-family actor outside the native spatial grid.

Footstep dispatch uses the original compiled `Step1`/`Step2` registry entries,
native RNG choice, native spatial-gain calculation, and `Sound_Play` call. The
audio observability hook records the dispatch independently of device output,
which lets the verifier keep game audio disabled.

Local/remote collision response now has one correction owner. It never moves
the packet-owned remote mirror. If the local player is actively moving into
that mirror, it moves only the local actor out to the sum of both native radii
plus the existing quarter-pixel padding. A stationary peer does not issue a
competing correction, so the old feedback oscillation does not return.

## #70 real stage model

Progress is a monotonic mapping of observed work. It is not time-based and does
not ease between values. The pre-game launcher and in-game renderer use the
same art and one nondecreasing scale. The launcher owns work that happens
before the game and its D3D9 device exist; the loader takes over at the
44-percent process handoff.

### Launcher stages

| Progress | Display label | Real source |
| ---: | --- | --- |
| 0.05 | Reading the host's grimoire... | `JoinPreview` is fetching the lobby join manifest and classifying its exact mod set against the local catalog/cache. |
| 0.10 | Waiting for your mod choice... | The join is blocked on the real host-mod consent decision. |
| 0.14 | Syncing the host's mods... | `PrepareSteamJoin` has entered `LobbyModSynchronizer`. Only progress tagged `LobbyModSync` can move this bar. |
| 0.15-0.22 | Downloading ... | Linear fraction of package bytes actually received from `WebsiteModPackageInstaller`. No new bytes means no movement. |
| 0.23 | Verifying ... | Package and content hash verification is executing. |
| 0.24-0.27 | Installing ... | Linear fraction of archive bytes extracted or required packages prepared; 0.27 means the exact host set completed. |
| 0.28 | Preparing this session... | Host-mod sync returned successfully and the exact session stage is being prepared. Hosts enter here while their staged game is prepared. |
| 0.34 | Entering the Steam lobby... | The launcher's Steam membership child is executing the requested lobby join. |
| 0.40 | Steam lobby joined. | The child reported joined/status for the requested lobby ID. |
| 0.44 | Opening Solomon Dark... | The staged game process launch has begun. |

Generic launcher-update progress is deliberately excluded. This prevents a
completed background update from claiming progress while the required host
package is still downloading. A late mod-progress message is also ignored once
session preparation has advanced beyond the mod-sync range.

Every transition compares against the current fraction and can only advance.
If a route, download, checkpoint, or participant stalls, its last honest label
and fraction remain unchanged. The 150 ms values in the implementation are
presentation gates only: they suppress flashes and allow the final, already
true participant-materialization stage to render before the hub handoff. They
never advance progress.

The native stage hooks were recovered at:

- arena-start dispatch `0x0063F460`;
- boneyard procedural create/save `0x0046D7B0`;
- boneyard loader `0x0046DC60`;
- boneyard generator `0x006388B0`;
- boneyard materialization `0x006531B0`.

The loader and procedural-create/save calls both pass a seven-DWORD by-value
path object and return with `ret 0x1c`. Their detours preserve all seven words;
this ABI is covered by static RE contracts.

## #70 rendering and lifetime

The shipped background is
`assets/loading/Wizards_dire_BG.png`, copied byte-for-byte from the approved
canonical asset. Its SHA-256 is
`251365e025129972707b436d441d52ae2c5f8199bc3f80a1c4e03b2a28a1180c`.
Launcher staging and release-package verification require that asset.

The pre-game WPF overlay embeds the canonical image as a resource and uses
`UniformToFill`; it exists because lobby preview, consent, and mod
download/verification all finish before the game process owns a D3D9 device.
The in-game loading screen is the final callback on the loader's shared D3D9
frame hook. Both renderers:

- cover-scales the 1920x1080 image and center-crops the excess;
- draws an approximately 18-percent-high bottom gradient ending at 70-percent
  black;
- centers the stage label above a 60-percent-width, 8-to-10-pixel gold-on-dark
  bar with a subtle border;
- remains hidden until a real load has lasted at least 150 ms;
- leave immediately at the launcher/game or loading/gameplay handoff.

The loader releases its managed texture and font through the shared D3D9
lifecycle.

Native boneyard loading is synchronous and blocks the ordinary frame loop.
Each native stage boundary therefore renders and presents one frame through
the already-hooked device after the 150 ms threshold. This does not install a
second device hook and does not alter
`native_d3d9_lifetime_guard.cpp`. Normal frame rendering resumes at gameplay
start, and completion immediately deactivates the overlay.

For reproducible evidence only, a staged launch may set
`SDMOD_LOADING_SCREEN_CAPTURE_DIRECTORY`. The renderer then captures the exact
backbuffer after the stage frame is drawn and before it is presented. The
setting is opt-in and absent from normal launches.

## #70 proof

`tools/verify_match_loading_screen.py` drives the real desktop join-preview and
`LobbyModSynchronizer` pipeline against an isolated local directory fixture.
Its 4 MiB package is paused at 1 MiB. The two paused captures are byte-for-byte
identical, proving the bar does not creep without new source bytes. It does not
launch the game.

`tools/verify_loading_screen.py` runs a live multiplayer host/join and a
transport-disabled single-player load with the required isolated instance
group, ports, and disabled audio. It validates launcher-to-loader scale
continuity, logged real-stage timelines, monotonic fractions, the 150 ms reveal
gate, canonical-background pixels, measured bar fill, exact staged-path
cleanup, and absence of nonempty crash artifacts. The multiplayer result's
client timeline advances from transport start at 0.44 through host settings
and checkpoints, native boneyard work, world/wave sync, and the run barrier
without resetting or regressing. It contains rendered client connection frames
at 0.66 and 0.92, plus a host-formation frame at the honest stage still active
after the 150 ms no-flash gate. Every captured frame has a measured bar
position matching its logged real fraction.

The machine-readable results are:

- `/mnt/d/codex-evidence/fieldfix-20260727/match-loading-screen-live.json`;
- `/mnt/d/codex-evidence/fieldfix-20260727/loading-screen-live.json`.

## Amendment (2026-07-27): the launcher window presents no loading screen

The owner directed that the desktop launcher itself must not display the
match loading screen; that presentation belongs to the staged game's D3D9
renderer only. The launcher-side pre-game presentation this note originally
described — the full-window art overlay, its bottom scrim, its dedicated
progress bar, the `MatchLoadingProgress` stage model, and the
`UpdateProgressScope` plumbing that fed it — was removed. The launcher keeps
its plain utility UI through join preview, consent, and lobby mod sync: the
existing status line and the standard update-progress presentation.

Nothing changed in-game: the D3D9 loading screen, its real native/join
stages, the 150 ms reveal gate, and the staged art materializer are exactly
as described above. `tools/verify_match_loading_screen.py` now proves the
inverse launcher property — the plain elements are visible, the overlay
signatures never appear, and a stalled download still holds an honest,
unchanged visible state. Its machine-readable result moved to
`/mnt/d/codex-evidence/launcher-plain-sync-20260727/match-loading-screen-live.json`.
The static contracts in `tests/re/static_re_boneyard_contracts.py` and
`tests/test_loading_screen_contract.py` enforce the launcher's overlay
absence so the presentation cannot silently return.
