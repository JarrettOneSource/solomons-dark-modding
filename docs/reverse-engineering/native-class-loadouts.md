# Native class loadouts and selection payload (loadre)

This is the implementation contract for the semantic payload of the retail
class picker. It closes the class/loadout part of browser-rebuild roadmap
section 6 against `SolomonDark.exe` SHA-256
`03a834566ce70fd8088f4cf9ee6693157130d8aec28c092cb814d6221231f1e3`.
An implementing agent can reconstruct every selectable class and the exact
state produced by choosing it without opening the binary.

The boundaries are deliberate:

- G11 owns the Create screen's layout, art placement, focus, and input. Import
  [the native menu contract](native-menus-and-boot.md); do not reconstruct that
  screen from the identifiers below.
- G13 owns when Create confirmation enters a fresh run/session. Import
  [the native session-flow machine](native-session-flow.md). This document owns
  the data carried across that edge and the actor initialization it causes.
- G6 owns what skill and Discipline ranks do during play and how they level.
  Import [the skill/Discipline contract](../re/skills-concentration-discipline.md).
  This document owns only which rows start active and which identity fields
  persist on the actor.
- G10 owns save serialization and migration. This document names the live
  fields that cross that boundary, but does not decode or prescribe a save
  format.

The checked-in live fixture is
[`class-loadout-goldens.json`](../../tests/fixtures/webgame/class-loadout-goldens.json).
It contains one independently launched retail recording for each of the 15
choices plus a mixed-class two-participant recording. The recorder is
[`record_native_class_loadout_goldens.py`](../../tools/record_native_class_loadout_goldens.py).
It only observes through the opt-in Lua-exec seam; it makes no gameplay change.

## Contract summary

A retail class is not an object type or one numeric `class_id`. It is this
product:

```text
ClassLoadout = ElementChoice x DisciplineChoice
ElementChoice = one of 5
DisciplineChoice = one of 3
```

`class_key`, such as `fire-mind`, is a portable fixture/browser key. It has no
native combined scalar equivalent. Keep these native namespaces distinct:

1. Create raw indices: element `0..4`, Discipline `0..2`;
2. `Skills_Wizard` book rows: element roots `0..4`, Discipline roots `5..7`,
   and spell rows such as `8` or `45`; and
3. multiplayer profile ids: element `0..4` in the order Fire, Water, Earth,
   Air, Ether and Discipline `0..2` in the order Mind, Body, Arcane.

Selection initializes one participant's own `Skills_Wizard` object. It never
writes a shared player stat book. Every local player, peer, and materialized bot
has an independent progression address and 83-row book, as required by the
[participant model](../multiplayer-participant-model.md#participant-owned-inventory-and-books).

## Book row ABI and raw regions

Each progression object owns its table pointer and count:

| Progression field | Meaning |
| --- | --- |
| `+0x20` | pointer to row 0 |
| `+0x24` | row count, exactly `83` for `Skills_Wizard` |

Rows have stride `0x70` bytes:

| Row offset | Width | Meaning |
| --- | ---: | --- |
| `+0x1C` | `u16` | family/root row |
| `+0x1E` | `u16` | unknown |
| `+0x20` | `u16` | base/permanent rank |
| `+0x22` | `u16` | effective rank |
| `+0x24` | `u8` | unknown |
| `+0x25` | `u8` | unknown |
| `+0x26` | `u8` | category |
| `+0x27` | `u8` | flags |
| `+0x64` | `f32` | current cooldown |
| `+0x68` | `f32` | cooldown cap |

Do not widen the four adjacent rank/family halfwords into convenient `i32`
fields. That would merge distinct native values. The live golden includes all
83 decoded rows and all `83 * 0x70 = 9296` raw bytes. Because row `+0x6C` is a
process address, the recorder also stores a normalized raw region with those
four pointer bytes zeroed in every row; its SHA-256 is stable and portable.

## Selection wiring: definition to actor

### What confirmation writes

The click handler `0x0058BCE0` searches exactly five element hit points and
three Discipline hit points. A click writes only the owning Create object:

| Create object field | Meaning |
| --- | --- |
| `+0x7C` | element point array, five entries of stride 8 |
| `+0x18C u8` | element selection enabled |
| `+0x1A4 i32` | selected raw element id |
| `+0xA4` | Discipline point array, three entries of stride 8 |
| `+0x228 u8` | Discipline selection enabled |
| `+0x22C i32` | selected raw Discipline id |

The Create tick `0x0058A820` publishes those raw values to
`DAT_0080807C` (element) and `DAT_00808080` (Discipline) and invokes the
new-character finalizer `0x005D0290`. This is the payload handoff. G13's session
machine owns the surrounding Create-confirmation-to-Courtyard transition and
states that the retained selection enters a fresh Courtyard actor.

### Complete definition-to-actor mapping

For the new local actor, `0x005D0290` resolves the selected tuple and applies
this exact mapping to the participant's own progression object:

| Definition field | Actor destination | Additional operation |
| --- | --- | --- |
| element root row | progression `+0x82C i32` | grant row through `0x00660320(row, 0)` |
| primary spell row | progression `+0x86C i32` | grant row through `0x00660320(row, 0)` |
| secondary spell row | progression `+0x870 i32` | grant through `0x00660320(row, 0)` and `0x005C85E0` when the native gate permits it |
| Discipline root row | progression `+0x830 i32` | grant row through `0x00660320(row, 1)` |
| every root row `0..7` | owned book rows `+0x20/+0x22` | grant in native order `0,2,1,3,4,6,5,7`; final rank is 1 |
| common scalar defaults | fields in the scalar table above | `Skills` `0x006594E0`, then `Skills_Wizard` `0x00674EE0` |
| common equipment/inventory | participant inventory and equip state | starter `0x005CFA80` |

`0x0065F9A0` refreshes derived state after the selected grants and again after
the eight root grants. The live capture waits until all fields, all rows,
inventory, equipment, and participant ledgers are present at the first
controllable tick; it does not mistake constructor allocation for completion.

The local actor linkage observed in every class capture is:

```text
PlayerWizard + 0x300 -> progression smart-pointer handle
handle inner object  -> that participant's Skills_Wizard
Skills_Wizard + 0x20 -> that participant's 83-row book
```

`sd.player.get_state().progression_address` agrees with the handle's inner
object. A standalone bot additionally exposes its direct progression at
`actor+0x200`; its `actor+0x300` handle resolves to the same bot-owned object.
Never resolve a peer's book through the local player's pointer.

## Init values versus persistent rules

There are no class-specific numeric HP, MP, movement, damage, resistance,
recovery, or equipment modifiers at initialization. All 15 live captures have
the identical common scalar and starter-item state above.

The class is nevertheless more than a disposable init table. Progression
`+0x82C` and `+0x830` remain the selected element and Discipline roots, and
`+0x86C/+0x870` retain the starting spell pair. Later `Skills_Wizard` behavior,
including vslot `+0x74 -> 0x0067CB70`, consumes the owned progression/book
state. A port must preserve these selectors as persistent per-actor rule inputs;
it must not translate a Discipline effect into a one-time stat increment.
The formula/effect semantics and leveling of those rows remain G6 territory.

The constructor-random `+0x834` slot and active-Weld `+0x844` value are
explicitly not class selectors. Their changing values across otherwise
identical class captures disprove such a mapping.

## Multiplayer and bots

### Peer replication

The wire-facing `MultiplayerCharacterProfile` carries semantic `element_id`,
semantic `discipline_id`, four native appearance/loadout choice ids when known,
loadout rows, level, and experience. Local capture translates progression roots
to semantic ids in
`multiplayer_local_transport/local_profile_loadout_capture.inl`; state and cast
packets replicate the profile. Remote materialization translates the semantic
ids back to native rows. This translation is required because Create raw ids do
not share the profile ordering.

Each peer keeps an independent actor, progression object, book, stats,
inventory, and equipment. Mixed classes have no shared class-stat state and no
cross-participant initialization interaction. Any shared gameplay consequence
comes later from the already-owned multiplayer authority/effect systems, not
from class selection.

### Bot assignment path

The tested bot seam is `sd.bots.create` with a semantic profile. Lua parsing
builds a `BotCreateRequest`; standalone materialization owns a fresh slot and
progression object. In
`standalone_materialization_selection_priming.inl`,
`NativeSkillRowForDiscipline`, `NativeSkillRowForElement`, and
`NativeStartingSecondaryRowForElement` translate profile ids. The materializer
primes every root and the semantic primary row. It only mirrors the four
`+0x82C/+0x830/+0x86C/+0x870` fields when all four explicit native appearance
choice ids are present. The live low-level bot request deliberately omitted
those ids, producing the exact result above.

Do not force the local Create finalizer's four-field result onto this bot path.
That would contradict the observed remote materializer. Higher-level bot APIs
may prefill a primary loadout entry, but the receiving actor still owns its own
book and follows the explicit-versus-semantic branch.

## Live golden method and provenance

The recorder launched 15 isolated `load-gold-*` retail instances plus the one
mixed case, using only UDP ports 52411 and 52412 and
`SDMOD_DISABLE_AUDIO=1`. It derived the source commit, dirty state, retail EXE
hash, and actually loaded DLL path/hash itself. No provenance field is accepted
as an argument.

Each snapshot is settle-gated on the structural payload: actor mapping, every
typed scalar, all 83 decoded rows, normalized raw regions, native inventory,
equipment, and participant-owned ledgers. A capture requires at least 40
consecutive byte-identical structural samples over at least two seconds. Tick,
app-tick, addresses, and the explicitly classified `+0x88C` meditation runtime
counter are retained but excluded from the structural digest. Every capture in
the fixture met the gate; the recorder aborts on any other changing field.

Readiness has separate retryable and terminal outcomes. A pipe that is not yet
ready is retried only while its exact launched process remains alive; a dead
process, unrunnable probe, malformed reply, or structurally unstable surface is
a hard failure. Each run receipt proves the exact owned PID and reserved ports
were absent before launch and absent again after cleanup.
