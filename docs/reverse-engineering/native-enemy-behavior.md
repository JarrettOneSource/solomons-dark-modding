# Native enemy behavior interpreter

## Scope and executable

This document is the gameplay-behavior contract for the browser rebuild. It
explains how a serialized `MonsterRecipe` becomes a live enemy brain: target
selection, movement, action scheduling, hit timing, damage dispatch, special
mechanics, and death. Sprite selection and animation presentation belong to
the sibling animation reconstruction. Death drops belong to the loot
reconstruction. Wave membership and scaling composition remain the authority
of [`data/wave.txt` and the wave scaling reconstruction](../wave-scaling-re.md);
they are cited here, not reconstructed again.

Addresses are for the supported retail `SolomonDark.exe`, SHA-256
`03a834566ce70fd8088f4cf9ee6693157130d8aec28c092cb814d6221231f1e3`.
The finite enemy census is generated by
`tools/build_native_enemy_catalog.py` and is cross-checked against
[`native-enemies.md`](native-enemies.md). A type is an enemy when the runtime
marks/tracks it as an enemy; multiplayer code must not replace that fact with
a type-ID whitelist.

## Construction pipeline

```text
MonsterRecipe::Sync 0x0063E890
  -> MonsterSetup_Parse 0x004AFBC0
  -> BuildEnemyConfig 0x0046B390
       applies arena HP/damage/chase/attack/XP scalars +0x9008..+0x9024
  -> factory/configure 0x005B7080 / 0x00463B50 / 0x00462790
  -> place and register 0x00469580
  -> target refresh 0x00483480
  -> common chase 0x004835F0 or a family-specific brain
  -> family action event
  -> contact-context setup 0x006246F0
  -> contact dispatch 0x0063E7D0
  -> target virtual +0x4C
```

Recipes are definitions, not actors. `0x00462790` copies the evaluated config
into family-specific live fields. Arena scalars are applied before that copy:
`+0x9008` multiplies HP; `+0x900C..+0x9018` multiply the four numeric damage or
duration lanes; `+0x901C` multiplies chase speed; `+0x9020` multiplies attack
speed; and `+0x9024` modifies XP. The browser interpreter should therefore
construct an immutable evaluated config, then instantiate mutable brain state.

a recovered actor/brain consumer. `definition-only` means it participates in
definition lookup or persistence but no per-tick brain consumer was found.

explicit `not-yet-reversed` verdict is deliberately different from zero or

## Target acquisition and switching

This section extends, and does not repeat, the landed
[`native-enemy-target-acquisition.md`](native-enemy-target-acquisition.md)
work.

- `MonsterPathfinding_SelectNearestTarget (0x00481A60)` scans the stock
  gameplay hostile-candidate list, rejects native-ineligible `+0x160` actors
  and invalid ActorWorld buckets, and chooses minimum Euclidean distance.
  There is no player-vs-bot weight: a living gameplay-slot human or bot is one
  geometric candidate. Slot 0 is appended explicitly by the loader because it
  lacks a `ParticipantEntityBinding`.
- `MonsterPathfinding_RefreshTarget (0x00483480)` derives the cadence from
  recipe field `+0xB9`, selects/reloads the target, faces it, and writes phase
  `hostile+0x1DC = tick % hostile+0x1E0`. The recovered cadence is 3 ticks for
  no recipe, 10 for mode 0, 3 for mode 1, and 10 for mode 3.
- `Badguy_CommonChaseTick (0x004835F0)` adds periodic, missing-bucket, and
  25-tick refresh lanes. Family brains may refresh less often; therefore the
  authoritative loader re-evaluates every tracked live scene enemy at most
  once per 100 ms. A newly nearer candidate can switch on that bounded edge.
- On target loss, the native refresh path tries selection, reloads the exact
  bucket identity, and either resumes approach or chooses a random heading.
  The loader also reacquires after ActorWorld unregister and repairs the
  native `0x00483895` post-selection clear. A dead slot-0 target observes the
  documented death-transition grace before mutation.
- Host authority alone chooses. Clients resolve and apply the host-authored
  participant ID, owner-plus-native-type identity, or exact native bucket.
  Manual freeze, Turn Undead, explicit Lua targets, and client snapshots have
  higher priority than default nearest selection.
- GoodImp reverses allegiance and chooses tracked hostiles. Golem is already a
  native candidate; GoodImp and Leviathan are explicit validated sidecars.
  This does not admit arbitrary world actors.

Live bot consequences are recorded in
[`beta31-hostile-targeting-class-2026-08-04.md`](../bugs/beta31-hostile-targeting-class-2026-08-04.md)
and
[`beta32-bot-mana-and-lone-target-handoff-2026-08-04.md`](../bugs/beta32-bot-mana-and-lone-target-handoff-2026-08-04.md):
gameplay-slot actors are targetable, a targetless hostile can acquire a lone
bot on the maintenance edge, and a hostile with a still-valid human target
switches only when the nearest-selection edge runs.

## Skeleton family: executable template

The interpreter has two layers. The locomotion brain chooses conceptual
states; attacks live in the actor's embedded action manager at `+0xDC`.
`actor+0xE4` is the queued-action count and `actor+0xF0` points at the list.
Each list entry points to a shared-pointer control block whose first word is
the action object. The action ID is `action+0x14` and fractional progress is
`action+0x30`. These are enemy-action offsets, not the player's control-brain
offset `+0x21C`. A consumer must reject an ambiguous multi-entry queue instead
of silently selecting one; all accepted behavior traces observed exactly one
entry while an attack was active.

### Required transition relation

The following is the browser state relation. `attack_active` is an event edge,
not an animation pose. An action can re-enter it when another native marker
fires; presentation may display several surrounding frames, but only the
listed native callbacks apply gameplay output.

Skeleton movement is `0x004773E0`, tick/schedule is `0x00484B90`, action
dispatch is `0x00473960`, and hit is `0x00477580`. Weapon mode chooses Claw
`0x0E`, ordinary weapon `0x0F`, or Pike `0x10`; sword, mace, flail, and axe
share the ordinary weapon timing but retain their evaluated damage/durability
changes. Armor/headgear do not add a new AI state. Death presentation differs
by equipment but the gameplay terminal state and reward entry are the same;
see [`skeleton-death-effects-re.md`](../skeleton-death-effects-re.md).

Archer movement/range control is `0x00477B40`/`0x00485200`, scheduling is
`0x00473B40`, and its active callback `0x00477B90` creates `Arrow 0x7DA`.
The arrow receives source/team, origin, heading, primary damage, and the
normal/fire/poison payload. Accuracy mode, extra-arrow count, multi-arrow mode,
and strafing are independent. Scatter directions use an actor-scoped RNG
seeded from actor `+0x1C0`; do not substitute browser `Math.random`.

There is one native presentation-to-gameplay latch that G4 must preserve at
the seam. Archer predicate `0x00477A80` rejects the shot until byte
`actor+0x248` is nonzero, a target exists, squared distance is less than
`(actor+0x1B0)^2`, and line-of-sight `0x00524D70` accepts. Render callback
`0x0048F450` raises `+0x248`; a truly headless retail run left it zero and the
Archer never queued `0x11`, while a visible run raised it to one and attacked.
The browser brain therefore needs an explicit presentation-ready input, not a
hidden dependency on whether a canvas happened to draw that frame.

Mage movement/range control is `0x00478380`/`0x00490860`, scheduling is
`0x00478290`, and active dispatch is `0x0047FDE0`. Element branches create
`Firebolt 0x7EB`, `GuidedMissile 0x7EC`, or run their recovered direct/status
contact paths. Self and ally shields have separate toggles/strengths and a
shared interval. The per-cast rate variance consumes the active shared native
RNG stream at `0x00818B08`.

### Attack timing and damage edge

At fixed actor delta 1, per-marker rate multiplier 1, and attack speed 1,
action progress increases by `base_rate * actor+0x17C` each native tick.
Completion is the first tick with progress strictly greater than the end
frame. The action code can reroll its marker-rate multiplier, so the first four
rows are nominal integer bounds for a multiplier of one, not a promise that a
live action always lasts that many wall ticks. The fixture preserves the
actual progress and event ticks.

`SkeletonAction_Tick 0x0044BC20` tests both native marker constants (`4.0` at
`0x007849F8` and `8.0` at `0x007849DC`) and invokes the family callback on a
crossing. The action can wrap at completion, so damage is not a single
presentation-frame Boolean. In the accepted stationary claw trace, the first
complete action starts at fixture tick 101, reaches the derived frame-4 marker
at 133, produces three separately observed `3.0` HP resolver events at ticks
133, 134, and 161, and leaves the queue at tick 162. Those are gameplay
events, not duplicated sprites; the static contract pins that exact witness.

The Skeleton active callback calls `0x006246F0`, stages damage/source in
`0x0081C6E0..0x0081C6F8`, and calls `0x0063E7D0(target)`. That dispatcher
checks same-world contact and invokes target virtual `+0x4C`; player damage
then proceeds through the landed authoritative player-damage hooks. This is
the same contact ABI documented in
[`native-projectile-and-spell-mechanics.md`](native-projectile-and-spell-mechanics.md#damage-application-path-and-accepted-goldens).
Projectile flight, collision queries, modifiers, and contact are owned by
[`native-projectiles-and-effects.md`](native-projectiles-and-effects.md) and
[`native-projectile-and-spell-mechanics.md`](native-projectile-and-spell-mechanics.md);
the enemy brain owns only when and with what payload the projectile is born.

family override (if any) followed by common reward handling; drop contents are
not repeated here. If a row omits windup, flee/leash, or a separate cooldown,
no distinct state was recovered for that family: use its stated contact or
timer edge and the common target-loss return to search rather than inventing
one.

## RNG contract for the browser

The primitive is the 55-word lagged-Fibonacci generator at `0x00401170`; float
draws use `0x00401310`. The active pointer is `0x00818B08`. Ordinary startup
seeds the shared global from `timeGetTime`; deterministic loader runs can seed
it through `sd.rng.set_seed`. Level/screen construction also has twelve
recovered seed sites using `App+0x28 * 0xEF3`, so elapsed unpaused app ticks are
part of native seed state. Full recurrence and float32 rounding are specified
in [`native-movement-and-tick.md`](native-movement-and-tick.md#native-rng).

Enemy construction normally consumes shared draws and places a derived seed
at actor `+0x1C0`. Most scheduling/wander decisions continue on the shared
stream. The recovered private exceptions relevant here are actor-seeded drop
selection and DemonSkull SpitFire; Archer scatter also scopes its aiming draws
to actor state. A browser rebuild must preserve both stream identity and draw
order. Removing a gameplay-adjacent presentation draw from the shared stream
without an equivalent advance changes later behavior.

The live recorder writes `RUN_SEED = 0x013579BD` to the shared stream before
`sd.hub.start_match`, but does **not** call that a complete run seed. Level
construction may reseed from `App+0x28 * 0xEF3` as documented by G1. Every
trace therefore records the spawned enemy's actual `actor+0x1C0` construction
seed and the first/last native tick. Replays key behavior rolls by the named
shared or actor-private stream, never by the requested seed alone.

## Live golden format

[`enemy-behavior-goldens.json`](../../tests/fixtures/webgame/enemy-behavior-goldens.json)
is recorded from a small owned retail instance by
`tools/record_enemy_behavior_goldens.py`. Each scenario records every native
tick's enemy position, conceptual/raw state fields, facing, action ID/progress,
target position, HP, attack events, projectile births, and observed damage
amounts. Skeleton, Archer, Mage, and Dire Faculty each run against both a
stationary local player and a deterministic moving local player driven by
`sd.input.hold_movement_frames`. The target moves in an 80-tick `+Y`, 120-tick
idle, 80-tick `-Y`, 120-tick idle cycle. The recorder primes the stock wave
spawner through `sd.gameplay.start_waves` and selects an exact stock group; it
never calls an enemy constructor directly. Faculty traces explicitly set only
its live secondary cooldown `+0x260` to `-1` so the native random scheduler can
exercise the special during the bounded window; that setup is recorded in
each trace.

Queue start/end events come from the native action manager, active markers are
labelled `derived_action_progress_marker`, projectile births come from native
world registration, and damage comes from the loader's before/after player
resolver observation. The committed fixture and standalone evidence copy are
byte-identical. Fixture SHA-256:
`f246c280e7fea7c90573eb6fcb2636adbc4e327f6f15b5caa12735bf0453a82e`.

The fixture is an acceptance oracle, not a replacement for the state tables:
one trace proves the executed branch and timing, while the static reconstruction
specifies the unexecuted config branches.

## Not Yet Reversed

- Recipe `+0x82`, `+0x98`, and `+0xA8` have no independent recovered live-brain
  copy. They must round-trip exactly but have no invented AI effect.
- The exact probability formulas for every family scheduler branch have not all
  been reduced to closed form. The table names the owning stream so a port can
  reproduce native draw order even where the human-readable probability is
  not yet simplified.
- Dire Faculty primary/secondary index 3 have editor labels but no executable
  event branch in `0x004804D0`; they are dormant, not missing browser work.
- GoodImp lifetime duration and several boss recovery frame constants remain
  executable-trace/state-machine facts rather than generalized recipe fields.
  Preserve the native trace behavior; do not infer them from unrelated fields.
